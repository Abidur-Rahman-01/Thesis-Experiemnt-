1. Motivation

The Rise of State-Mutating Autonomous Agents

Tool-using agents do not just converse—they persistently alter digital environments

Agents in benchmarks like SWE-bench Verified routinely modify files, execute bash scripts, install packages, and invoke APIs. However, tool operations possess radical asymmetry:

Inspect / Passive

cat file.py, ls -la, grep

Deterministic zero side-effects. Safe to execute freely without compute overhead.

Reversible Mutation

git branch, editing unit tests

Local mutations. Can be undone via local VCS checkpoints if caught early.

High Impact / Irreversible

rm -rf, git push --force, DB drops

Severe blast radius. Permanent state corruption or credential leakage.

2. The Problem

The Verification Dilemma: Failure of Extremes

Why naive agent architectures fail under real-world constraints

Extreme A: Never Verify (Fragile)
  • Low inference latency and minimal token consumption.
  • A single erroneous edit compounds down 30+ steps.
  • Silent failures corrupt execution state permanently.
  • Result: Poor overall benchmark resolution.
Extreme B: Always Verify (Unusable)
  • Reflexion / step-wise LLM judge after every single action.
  • Inference cost balloons 3x to 10x.
  • Verifier Noise: A 10% false alarm rate on 20 steps leads to premature run rejection.
  • Result: Exhausts token & API budget rapidly.
The Scientific Challenge: Given bounded compute, WHICH actions must be verified before execution?
3. Research Questions

Primary Research Questions & Hypotheses

A mathematically grounded, falsifiable thesis framing

Primary Question: Under a fixed verification compute budget, can a risk-calibrated value-of-verification controller catch more consequential errors than simpler uncertainty-only, impact-only, or simple product policies?
RQ1: Calibration Viability

Can step-level error probability $p_{e,t}$ be reliably calibrated in tool-use loops using held-out temperature scaling?

RQ2: Budgeted Allocation

Does selective gating catch significantly more consequential errors per unit compute than uniform or random spend?

RQ3: Mandatory Falsifiable Baseline

Does full RC-VoV beat the simple product baseline $v_t = \mathbf{1}[p_{e,t} I_t > \tau_{\text{PI}}]$ under matched compute?

RQ4: Counterfactual Recovery

Does local rollback to cryptographic checkpoints reduce recovery loss $\rho_t$ compared to restarting from step 0?

6. Architecture Deep Dive

Typed Action Contracts & Impact Scoring

Moving beyond raw strings to typed, verifiable contracts

1. The ActionContract Schema

Every tool action is encapsulated with execution metadata:

@dataclass(frozen=True)
class ActionContract:
    action_id: str
    action_class: ActionClass
    operation: str
    arguments: dict
    mutates_state: bool
    is_reversible: bool
    requires_checkpoint: bool
2. Multi-Dimensional Impact ($I_t$)

Normalized feature vector $x_t \in [0, 1]^7$:

  • mutation: modifies persistent state?
  • irreversibility: can state be restored?
  • privilege: requires root / elevated privileges?
  • external: outside sandbox blast radius?
  • secret: touches credentials / env vars?
  • scope: affects multiple directories?
$$I_t = \operatorname{clip}(w^\top x_t, 0, 1)$$
7. Mathematical Core

Risk-Calibrated Value-of-Verification (RC-VoV)

Decision-theoretic derivation of expected verification benefit

We compare expected future loss under both execution pathways:

Loss Without Verification
$$L_t^{\text{no-verify}} = p_{e,t} I_t$$

Product of calibrated error probability and action impact.

Loss With Verification
$$L_t^{\text{verify}} = C_{v,t} + p_{e,t}[(1 - d_t)I_t + d_t \rho_t I_t] + (1 - p_{e,t})f_t C_{fp,t}$$

Verification cost + missed error loss + recovered loss + false alarm penalty.

$$\boxed{\Delta_t = p_{e,t} d_t (1 - \rho_t) I_t - C_{v,t} - (1 - p_{e,t}) f_t C_{fp,t}}$$
Net Value of Verification = Avoided Consequential Loss − Verification Cost − False Alarm Penalty
8. Control Policy

Dynamic Budget Controller & Mandatory Baselines

Adaptive thresholding under hard compute bounds

Dynamic Marginal Utility Gate

Given remaining budget $B_t$ and initial budget $B_0$:

$$m_t = \frac{\max(\Delta_t, 0)}{C_{v,t} + \epsilon}, \quad \lambda_t = \lambda_0 \left[1 + \kappa \left(1 - \frac{B_t}{B_0}\right)\right]$$

Decision: Verify if $\text{hard-critical}_t \lor (m_t \ge \lambda_t \land \Delta_t > 0)$.

The Mandatory Falsifiable Baselines

RC-VoV must beat these at equal compute spend:

  • $p_e \times I$ Baseline: $v_t = \mathbf{1}[p_{e,t} I_t > \tau_{\text{PI}}]$
  • BAVAR-Style Baseline: Expected value without rollback recovery.
  • Confidence-Only Baseline: $v_t = \mathbf{1}[p_{e,t} > \tau]$.
  • Random Budget-Matched: Randomly selects until budget exhausted.
9. Architecture Deep Dive

Checkpointing & Counterfactual Recovery

Transactional state restoration without cold restarts

       Step t-1                     Step t (Proposed Action)                   Step t+1
   [ Verified State ] ───► [ Take Workspace Snapshot (SHA-256) ]
                                         │
                                         ▼ Execute in Sandbox
                                [ Action Evaluation ]
                                   ├── Success ──► Advance trajectory to t+1
                                   └── Falsified / Execution Error
                                         │
                                         ▼
                            [ Transactional Rollback ]
                                         │
                            Revert filesystem to SHA-256 digest
                                         │
                                         ▼
                         [ Counterfactual Continuation ]
                            Prompt policy for alternative a'_t
Why this matters for $\rho_t$: When an action fails, cold-restarting discards all prior valid reasoning. Checkpoint recovery restores state in milliseconds, minimizing recovery loss $\rho_t$.

13. Roadmap: Phases 1 & 2

Phase 1 & 2: Infrastructure & Data Manifest

Hardware validation, sandboxing, and non-circular data hygiene

Phase 1: Local RTX 5080 & Docker
  • Local Verifier: Deploy Qwen2.5-Coder-7B / Llama-3.1-8B via vLLM on RTX 5080 (16 GB).
  • VRAM Safeguard: Enforce operational limit: $$M_{\text{peak}} \le 0.90 \times M_{\text{VRAM}} \quad (\le 14.4\text{ GB})$$
  • Docker Sandbox: Zero network by default, strict memory (4 GB) and execution timeouts.
Phase 2: SWE-bench Verified Trajectories
  • Curate 150 tasks from SWE-bench Verified with high mutation rates.
  • Use capable frontier policy (Claude 3.5 / GPT-4o) to generate realistic trajectories.
  • Dual-Annotator Ground Truth: Record ground-truth labels $Y_t \in \{0, 1\}$ independently without circular verifier dependence.
14. Roadmap: Phase 3

Phase 3: Calibration & Empirical Statistics

Estimating parameters empirically rather than assuming them

1. Held-Out Temperature Scaling

Fit optimal $T^*$ by minimizing NLL on frozen calibration split ($N_{\text{cal}} \ge 300$):

$$T^* = \operatorname*{arg\,min}_{T > 0} -\sum_{i=1}^{N_{\text{cal}}} [y_i \log \sigma(z_i/T) + (1 - y_i)\log(1 - \sigma(z_i/T))]$$

Report Expected Calibration Error (ECE) and Brier Score.

2. Class-Level Verifier & Recovery Tables

Measure empirical characteristics per action class:

  • Detection Power ($d_t$): TPR on labeled buggy actions.
  • False Alarm Rate ($f_t$): FPR on valid actions.
  • Residual Loss ($\rho_t$): Measured task loss after rollback and branch continuation: $$\rho_t = 1 - \frac{\text{Success Rate}_{\text{after rollback}}}{\text{Success Rate}_{\text{clean}}}$$
15. Roadmap: Phase 4

Phase 4: Matched-Budget Replay & The Stop Rule

Testing the core hypothesis across verification budget tiers

Sweep Budgets $\mathcal{B} \in \{0\%, 10\%, 25\%, 50\%, 75\%, 100\%\}$ across All Schedulers
Measure Consequential Errors Caught per Verification Compute Token
The Pre-Registered Scientific Stop Rule

If RC-VoV does not achieve statistically significant higher allocation efficiency than the simple product baseline $p_{e,t} I_t$ on held-out replay:

  • We will simplify the controller down to $p_e \times I$ rather than adding ungrounded complexity.
  • We will report this transparently as a scientific finding: impact and uncertainty dominate verifier noise in practice.
16. Roadmap: Phase 5

Phase 5: Recovery Ablation & Online Evaluation

Validating counterfactual recovery and end-to-end task success

Controlled Recovery Experiment

Compare 3 recovery conditions on identical errors:

  • Cond A (Blind): Continue through error without rollback.
  • Cond B (Restart): Abort and restart from step 0.
  • Cond C (VERITAS): Rollback to SHA-256 snapshot and branch.

Hypothesis: Cond C preserves >70% inference tokens while matching task success.

Power Analysis & Online Validation
  • Execute 30-task pilot to measure empirical effect size $\delta$ and variance $\sigma^2$.
  • Calculate minimum sample size $N$ for $80\%$ statistical power ($\alpha = 0.05$).
  • Deploy Top-3 Schedulers online to measure real-world task resolution vs overall inference spend.
